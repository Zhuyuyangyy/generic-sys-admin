### 2.2 技术难点解决

**难点1：MinIO不可用时的系统稳定性**

问题：系统依赖MinIO作为文件存储，一旦MinIO服务不可用，整个上传功能瘫痪。

解决：引入策略模式 + MinioAvailability状态检测。系统启动时检测MinIO可用性并写入状态Bean，上传时根据状态自动选择MinIO或本地存储。整个过程对业务代码透明，无需if-else硬编码。

**难点2：无API Key时TTS功能无法调试**

问题：没有Minimax API Key时，TTS接口无法调用，接口返回500错误，影响开发调试。

解决：定义TtsService接口，MinimaxTtsUtil和MockTtsServiceImpl分别实现。通过@ConditionalOnProperty控制注入：无Key时注入Mock实现，有Key时注入真实实现，业务代码无感知。

**难点3：通用性与定制化的平衡**

问题：系统太通用则无特色，太定制则不通用。

解决：采用"三层架构"：核心层（BaseEntity/BaseController，不可改）+ 业务层（Service/Mapper，可定制）+ 配置层（菜单/角色数据，配置即生效）。

## 三、技术难点与解决过程

### 3.1 雪花算法主键冲突问题

**问题描述**：
初期使用MyBatis-Plus默认的雪花算法，但多实例部署时出现了主键冲突。

**解决过程**：
1. 分析原因：雪花算法依赖workId，多实例如果workId相同则可能冲突
2. 查阅资料：MyBatis-Plus的雪花算法支持通过配置workId来区分实例
3. 解决方案：在application.yml中配置 `mybatis-plus.generator.id-type: assign_id`，使用MyBatis-Plus自带的分布式ID生成器

**收获**：
理解了分布式ID生成的原理（时钟回拨、workId分配等问题），为以后解决分布式系统问题打下基础。

### 3.2 前端代理跨域问题

**问题描述**：
开发环境Vite代理配置了/api到8080后端，但生产环境Nginx配置不当时出现404。

**解决过程**：
1. 开发环境：Vite proxy自动处理，无问题
2. 测试环境：发现Cookie无法传递，原因是Proxy反向代理丢失了Origin头
3. 解决方案：后端配置CORS允许特定来源，前端请求带上withCredentials
4. 生产环境：Nginx配置 `proxy_set_header Host $host` 确保原始域名传递

**收获**：
深入理解了CORS机制和Nginx反向代理的原理，区分了开发环境和生产环境的差异。

## 四、心得体会

### 4.1 架构设计的重要性

这次项目让我深刻体会到"好的架构是设计出来的，不是重构出来的"。在项目初期，我们花了大量时间讨论架构设计：分层结构、模块划分、技术选型。虽然当时觉得进度慢，但后期开发非常顺畅，新功能可以快速接入。

### 4.2 文档先行的好处

这次写毕设文档的过程，让我意识到文档不仅是给评委看的，更是对自己设计的检验。很多在写文档时发现的设计缺陷，在编码阶段就被修正了。

### 4.3 降级思维的重要性

系统设计中一定要考虑"降级"：MinIO不可用怎么办？没有API Key怎么办？这些都是真实生产环境中会遇到的问题。策略模式+状态检测是一个很好的降级实现方式。

### 4.4 持续集成的价值

虽然这次项目没有完整的CI/CD，但我在本地建立了"改代码→编译→启动→测试"的快速循环，大幅提高了调试效率。
